# Оценка загруженности дороги по аэроснимку

Цель проекта — обнаруживать транспортные средства на аэроснимке,
анализировать их количество и плотность на участке дороги и определять
уровень загруженности.

Сейчас реализован первый этап: асинхронное приложение на FastAPI,
проверки состояния приложения и PostgreSQL, версия приложения и тесты.
Детекция транспорта и оценка загруженности пока не реализованы.

Источники данных для следующих этапов:

- [Aerial Multi-Vehicle Detection Dataset](https://zenodo.org/records/7053442)
  — аэроснимки с разметкой автомобилей, автобусов и грузовиков.
- [VisDrone](https://github.com/VisDrone/VisDrone-Dataset)
  — изображения и видео с дронов с разметкой объектов, включая транспорт.

## Стек

- Python 3.12+, uv — управление проектом и зависимостями.
- FastAPI и Uvicorn — HTTP API и ASGI-сервер.
- asyncpg — асинхронный доступ к PostgreSQL.
- Pydantic Settings — конфигурация из окружения и `.env`.
- Ruff — статический анализ и форматирование.

Зависимости разделены на группы `web` и `dev`. Обе группы устанавливаются
по умолчанию командой `uv sync`.

## Локальный запуск

Потребуются Python 3.12 или новее, установленный uv и доступный PostgreSQL.
Команды выполняются из корня репозитория.

1. Установите проект и зависимости из lock-файла:

   ```bash
   uv sync --frozen
   ```

2. Создайте в корне файл `.env` и укажите параметры своей БД:

   ```dotenv
   DATABASE__DATABASE_URL=postgresql://postgres:postgres@localhost:5432/mlops
   DATABASE__DB_POOL_MIN_SIZE=0
   DATABASE__DB_POOL_MAX_SIZE=10
   DATABASE__DB_COMMAND_TIMEOUT=5
   ENVIRONMENT=development
   LOG_LEVEL=INFO
   ```

   Имя пользователя, пароль, адрес и имя базы в примере замените своими.
   База должна быть создана заранее. Файл `.env` исключён из Git.

3. Запустите приложение:

   ```bash
   uv run uvicorn health.main:app --host 127.0.0.1 --port 8000 --reload
   ```

Swagger UI доступен по адресу <http://127.0.0.1:8000/docs>.

## Конфигурация

Настройки читаются из переменных окружения и `.env`; переменные окружения
имеют приоритет. Двойное подчёркивание отделяет вложенные поля.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `DATABASE__DATABASE_URL` | Обязательная | Строка подключения к PostgreSQL |
| `DATABASE__DB_POOL_MIN_SIZE` | `0` | Минимальное число соединений |
| `DATABASE__DB_POOL_MAX_SIZE` | `10` | Максимальное число соединений |
| `DATABASE__DB_COMMAND_TIMEOUT` | `5.0` | Таймаут SQL-команд в секундах |
| `ENVIRONMENT` | `development` | `development`, `staging` или `production` |
| `LOG_LEVEL` | `INFO` | `DEBUG`, `INFO`, `WARNING` или `ERROR` |

Поля `ENVIRONMENT` и `LOG_LEVEL` пока только загружаются в настройки:
отдельная настройка логирования через них не реализована.

## API

### `GET /healthz`

Быстрая проверка того, что процесс отвечает. Не обращается к БД.
При работающем приложении возвращает HTTP 200:

```json
{"status": "healthy"}
```

### `GET /api/v1/version`

Возвращает HTTP 200 и версию установленного пакета `mlops-health-service`.
Источник версии — метаданные проекта из `pyproject.toml`.

Имя Python-пакета для импортов — `health`, а имя устанавливаемого проекта —
`mlops-health-service`. Связь между ними задана параметром
`module-name = "health"` в настройках сборки `pyproject.toml`.

```json
{"version": "0.1.0"}
```

Проект должен быть установлен, например командой `uv sync`, чтобы его
метаданные были доступны через `importlib.metadata`.

### `GET /api/v1/health`

Получает соединение из общего пула и выполняет `SHOW server_version`.
Время проверки включает ожидание соединения и выполнение запроса;
общий таймаут этой операции — 5 секунд.

При успехе возвращает HTTP 200. Пример ответа:

```json
{
  "status": "healthy",
  "database": "connected",
  "response_time_ms": 2.35,
  "db_version": "17.0"
}
```

При ошибке или превышении таймаута возвращает HTTP 503:

```json
{
  "status": "unhealthy",
  "database": "disconnected",
  "response_time_ms": 5001.42,
  "db_version": null
}
```

Числа времени и версия PostgreSQL приведены для примера. Ошибка проверки
записывается в лог со стеком вызовов.

Пул создаётся в lifespan при старте приложения и закрывается при завершении.
Ошибка создания пула может прервать запуск приложения; в таком случае
HTTP-эндпоинты ещё недоступны.

Проверить ответы можно через Swagger UI или терминал:

```bash
curl http://127.0.0.1:8000/healthz
curl http://127.0.0.1:8000/api/v1/version
curl -i http://127.0.0.1:8000/api/v1/health
```

## Проверка оформления

```bash
uv run ruff check src tests
uv run ruff format --check src tests
```

Для применения форматирования:

```bash
uv run ruff format src
```

Ruff настроен на Python 3.12 и длину строки 100 символов. Проверяются
импорты, аннотации, именование и другие правила из `pyproject.toml`.

## Тесты и покрытие

Установите зависимости командой `uv sync --frozen`. Для полного набора
нужны работающий Docker Engine и Docker Compose 2.24.4 или новее
(используется `!override` для портов). Затем запустите:

```bash
uv run pytest
```

Эта же команда подходит для CI на runner с Docker и Compose. При первом
запуске потребуется доступ к реестрам образов и зависимостей.
Тесты собирают Dockerfile и запускают настоящий PostgreSQL через Compose
в отдельном проекте со случайным именем, свободными портами и собственным
томом. В конце временные контейнеры и том удаляются; сборочный кэш остаётся.
При недоступном Docker интеграционные тесты завершаются ошибкой.

Если на Linux сборка не может скачать зависимости из-за сети Docker,
можно явно использовать сеть хоста только для сборки:

```bash
uv run pytest --build-network=host
```

По умолчанию тесты используют обычную сеть сборки Docker. Сеть запущенных
приложения и БД при этом остаётся отдельной сетью тестового Compose-проекта.

Быстрые проверки без Docker:

```bash
uv run pytest -m "not integration"
```

Только проверки Docker и PostgreSQL:

```bash
uv run pytest -m integration
```

Настройки в `pyproject.toml` автоматически включают измерение покрытия строк
пакета `health`. В терминале появится таблица с непокрытыми строками.
Файл данных `.coverage` исключён из Git.

Для запуска одного набора тестов:

```bash
uv run pytest tests/test_api.py
```

Чтобы проверить отдельный тест без измерения покрытия:

```bash
uv run pytest tests/test_api.py::test_health_success --no-cov
```

### Как устроены проверки

- `tests/conftest.py` создаёт фикстуры — подготовку окружения для каждого
  теста. `database` подменяет создание пула и ответы соединения с помощью
  `AsyncMock`. `client` запускает приложение через `TestClient` вместе с
  настоящим lifespan и закрывает его после теста.
- `tests/test_api.py` отправляет HTTP-запросы внутри процесса, проверяет
  коды и JSON трёх эндпоинтов. Проверяются успешный запрос к БД, ошибка
  получения соединения, ошибка SQL-запроса и таймаут на обоих этапах.
  Для проверки округления времени подменяется таймер. В тестах таймаута
  реальное асинхронное ожидание отменяется через сокращённый до 0.01 с
  таймаут, чтобы не ждать по пять секунд.
- `tests/test_lifespan.py` проверяет параметры и однократное создание пула,
  закрытие при обычном завершении и исключении, а также отказ запуска
  при ошибке создания пула.
- `tests/test_config.py` проверяет значения по умолчанию, обязательный URL,
  ограничения чисел, допустимые варианты настроек и приоритет окружения
  над временным `.env`.
- `tests/test_integration.py` собирает и запускает настоящий образ,
  проверяет все три эндпоинта по HTTP, Docker healthcheck и пользователя
  контейнера. Версия БД сравнивается с результатом независимого запроса
  через asyncpg. Проверяется и локальное приложение с настоящим пулом БД.
  Остановка PostgreSQL должна дать 503, сохранив доступность `/healthz`;
  после запуска БД проверяется восстановление ответа 200.

`assert` сравнивает фактический результат с ожидаемым. `pytest.raises`
проверяет ожидаемые исключения. `monkeypatch` автоматически отменяет
подмены после теста, а `pytest.mark.parametrize` запускает одну проверку
с несколькими наборами входных данных. `AsyncMock` позволяет проверить,
что асинхронный вызов действительно ожидался через `await`.

Покрытие измеряет Python-код, выполненный в процессе pytest. Вызовы
приложения внутри Docker проверяются через HTTP, но в процент покрытия
не включаются. Для проверки реального подключения под coverage есть
отдельный тест локального приложения с настоящим PostgreSQL.
